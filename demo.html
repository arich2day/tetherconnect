The developer loop

Five beats.
One developer.
One audit trail.

The same five beats scripts/demo-dry-run.js posts against a live Overwatch. Each beat shows what runs, what's recorded, and the line of code that owns the decision.

Beat 01

Developer hits Claude Code from a laptop.

The coding agent reads HTTP_PROXY from its environment, opens a connection to 127.0.0.1:11435, and forwards a POST to /v1/messages. No agent-side cooperation is required; the env var is enough.

claude-code · ~/repo · session 7a3

Beat 02

Connect proxy classifies.
Deterministic floor + sampled judge.

The proxy runs Tier 0 against the request body. If a pattern matches, the request is dead at 403 and the forward path is not reached. If the floor is clear and the request is sampled, the judge runs — sync if the operator opted in to Tier 1, async-only otherwise.

tether-proxy · 127.0.0.1:11435 · v42

Beat 03

JIT control fires.
Workspace daemon pauses the action.

The developer reaches for the clipboard. The workspace daemon's policy axis on clipboard.mode is set to request in this tenant. The daemon does not forward "yes" or "no" — it posts a JIT_ACCESS_REQUEST to Overwatch and waits.

tether-workspace · /api/v1/workspace/decide

Beat 04

Operator decides in /access-requests.

The request lands in the Overwatch JIT queue. The operator sees who, what, when, and the matched controls. Approve or deny. The decision is auditable; the developer's IDE long-polls the wait URL and unblocks.

Beat 05

Developer unblocks.
Decision is auditable.

The IDE's long-poll on the wait URL returns decision: approved. The clipboard paste proceeds. Two records persist: a JIT_ACCESS_DECISION event in your SIEM and the policy-audit.jsonl line that authored the active version. An auditor pulls both — plus the signed bundle for version 42 — and verifies offline.
